# Patrol ledger changes with stat-only signatures

The watch loop that reloads ledgers on save will detect change by stat identity only: each poll stats the entry file, every file of the latest attempted include graph, and every path recorded by an `E-INCLUDE-READ` diagnostic, and rebuilds when any size or modification time changes. The previous patrol re-read and re-hashed the full contents of every graph file on every 250 ms tick; on a 5.6 MB, 5.25万-transaction ledger that cost ~6.5 ms per tick (≈2.6% of a core and ~25 MB/s of disk traffic) purely to answer "did anything change". Stat-only patrol costs tens of microseconds per tick regardless of ledger size, because a previously missing include target is statted too, its later appearance is still detected, and include-structure edits are caught through the edited file's own timestamp.

The per-poll content hash is deliberately dropped. A rewrite that preserves both size and nanosecond mtime is the only blind spot, modern filesystems timestamp writes at nanosecond granularity, and every mainstream watcher (including the event-based alternative) relies on the same mtime signal. Reintroducing eager reads to close that theoretical gap would spend real CPU and disk on every idle tick to defend against an event practical editing tools do not produce.

An event-based watcher (fsnotify or equivalent) was considered and deferred: it would add the repository's first third-party dependency to a dependency-free module, and rename-swap saves used by several editors plus network/sync-mounted ledgers are known weak spots of directory notifications. Stat polling over the graph keeps behavior identical across mounts and editors. If idle cost ever matters again at much larger file counts, the escalation is per-file watch descriptors, not a return to full-content reads.

Acceptance is locked by tests and a benchmark: change detection (edits, deletions, and a previously missing include target appearing) is covered by automated tests, and `go test -bench=WatchSignature ./internal/snapshot` must stay under 0.1 ms per poll on the reference shape, versus ~6.5 ms before.
